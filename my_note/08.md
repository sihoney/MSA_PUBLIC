# github actions / cicd / pipeline / runner 차이 & jobs vs step

좋다. 지금 네 이해 거의 맞는데, **딱 몇 군데만 바로잡으면 완벽해진다.**
짧고 직관적으로 정리해줄게.

---

# 🔥 전체 구조 한 방 정리

```text
GitHub Actions (플랫폼)
  → Workflow (= Pipeline)
    → Job
      → Step
```

---

# 🧠 1️⃣ GitHub Actions

👉 네 말:

> “제 3의 OS?”

👉 ❌ 살짝 틀림
👉 ✅ 정확히는:

> **“코드를 실행해주는 자동화 플랫폼 (클라우드 실행 환경)”**

---

## ✔️ 핵심

* OS가 아니라
  👉 **OS(러너)를 빌려주는 서비스**

---

# 🧠 2️⃣ Runner (중요)

👉 이게 진짜 OS임

```text
runs-on: ubuntu-latest
```

👉 GitHub가 VM 하나 만들어줌

---

## ✔️ 정리

👉 GitHub Actions = 플랫폼
👉 Runner = 실제 실행되는 OS

---

# 🧠 3️⃣ Pipeline (= Workflow)

👉 네 말:

> “pipeline = runner?”

👉 ❌ 아님
👉 ✅

> **Pipeline = 실행 시나리오 (YAML 파일)**

---

## ✔️ 예

```yaml
on: push
jobs:
  build:
  test:
```

👉 이게 pipeline

---

# 🧠 4️⃣ Job

👉 네 말:

> “한 OS에서 실행되는 일 묶음?”

👉 ❌ 반만 맞음
👉 ✅ 정확히:

> **Job = 하나의 독립된 실행 단위 (각각 별도 VM)**

---

## 💥 핵심 포인트

👉 job 하나 = VM 하나

---

## ✔️ 예

```yaml
jobs:
  build:
  deploy:
```

👉 build, deploy → 각각 따로 실행됨

---

# 🧠 5️⃣ Step

👉 네 말:

> “논리적 구획?”

👉 ❌ 아님
👉 ✅

> **Step = 실제 실행 명령 (쉘 / 액션)**

---

## ✔️ 특징

* 같은 job 안에서
* 같은 OS에서 실행됨

---

## ✔️ 예

```yaml
steps:
  - checkout
  - build
  - docker push
```

👉 순차 실행

---

# 🔥 너 개념 교정 (핵심)

## ❌ 너 생각

* pipeline = runner ❌
* job = 같은 OS ❌

---

## ✅ 실제 구조

```text
Workflow (Pipeline)
  ├── Job A (VM 1)
  │     ├── Step 1
  │     ├── Step 2
  │
  ├── Job B (VM 2)
        ├── Step 1
        ├── Step 2
```

---

# 🔥 핵심 차이 (진짜 중요)

| 개념       | 의미             |
| -------- | -------------- |
| Workflow | 전체 자동화 흐름      |
| Runner   | 실행되는 VM        |
| Job      | VM 하나          |
| Step     | VM 안에서 실행되는 명령 |

---

# 💡 직관 비유

## 🍳 요리 비유

* GitHub Actions → 주방 시스템
* Workflow → 레시피
* Job → 요리사 1명 (각자 주방)
* Step → 요리 과정 (재료 손질, 굽기 등)

---

# 💬 한 줄 정리

👉 **Job = 실행 환경 단위 (VM)**
👉 **Step = 그 안에서 실행되는 명령**

---

# 🔥 너 수준에서 가장 중요한 포인트

👉 “Job은 서로 환경 공유 안 한다”

이거 모르면 나중에 CI/CD 꼬인다.

---
