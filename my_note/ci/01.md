# image-registry-cicd.yml

## 의도, 목적

각 서비스별 이미지를 자동으로 만들어 레지스트리에 저장하는 구조 
"GHCR까지 올리는 것"

## 흐름

```
개발자 PUSH
-> Github Actions 실행
-> 러너(ubuntu-lastest)가 코드 checkout
-> Docker image build
-> GHCR에 PUSH
-> 나중에 서버가 있으면 그 서버가 그 이미지를 PULL해서 실행
```

---

## image-registry-cicd.yml 설명

> 메인 브랜치 계열용 공용 이미지 빌드 워크플로

```yml
on:
  # GitHub Actions 화면에서 버튼으로 직접 실행할 수 있게 한다.
  workflow_dispatch:
  push:
    # main 또는 master에 코드가 들어올 때 자동으로 동작한다.
    branches:
      - main
      - master
    # 아래 경로가 바뀐 경우에만 실행해서 불필요한 빌드를 줄인다.
    paths:
      - "config/**"
      - "discovery/**"
      - "apigateway/**"
      - ".github/workflows/image-registry-cicd.yml"
```

- push.branches: 변경 감지되는 이벤트 타입 지정
- push.paths: 변경 감지되는 위치 지정
- workflow_dispatch: 수동 실행

---

```yml
concurrency:
  # 같은 workflow가 연속으로 실행되면 이전 작업을 취소하고
  # 가장 최신 코드 기준 실행만 남기도록 한다.
  group: image-registry-cicd
  cancel-in-progress: true
```

- concurrency.group
- concurrency.cancel-in-progress
: 같은 워크플로가 연속 실행되면 **이전 실행을 취소하고 최신 커밋 기준 실행만 남긴다.**

---

```yml
permissions:
  # 저장소 코드를 checkout 하려면 읽기 권한이 필요하다.
  contents: read
  # GHCR에 이미지를 push 하려면 packages 쓰기 권한이 필요하다.
  packages: write
```

- contents: read -> 코드를 checkout하기 위한 읽기 권한
- packages: write -> GHCR에 이미지 push하기 위한 패키지 쓰기 권한

Github 문서도 `GITHUB_TOKEN` 사용 시 권한을 명시적으로 조정할 수 있다고 설명

---

```yml
jobs:
  build-and-push:
    # matrix로 서비스별 작업이 나뉘므로
    # Actions 화면에서 어떤 서비스가 실행 중인지 바로 보이게 이름을 붙인다.
    name: "${{ matrix.module_name }} 이미지 빌드 및 푸시"
    # GitHub가 제공하는 리눅스 실행기를 사용한다.
    runs-on: ubuntu-latest
    strategy:
      # 한 서비스가 실패해도 다른 서비스 빌드는 계속 진행하게 한다.
      fail-fast: false
      matrix:
        # include를 쓰면 서비스별 폴더 경로와 이미지 이름을 한 번에 관리할 수 있다.
        include:
          - module_name: config
            module_dir: config
            image_name: config
          - module_name: discovery
            module_dir: discovery
            image_name: discovery
          - module_name: apigateway
            module_dir: apigateway
            image_name: apigateway
```

- jobs.build-and-push: 하나의 job
- strategy.matrix.include: config, discovery, apigateway 세 모듈을 돌리게 해놨다.

> 즉 **같은 작업 틀을 서비스별로 반복 실행**하는 방식
> 이게 matrix의 핵심, "job을 세 번 복붙하지 말고, 변수만 바꿔서 반복해라"
> 각 모듈을 대상으로 동일한 작업이 각각 실행되는 것

---

```yml
    steps:
      # 현재 저장소 코드를 runner로 내려받는다.
      # 이 단계가 있어야 Gradle 빌드와 Docker 빌드에 필요한 파일을 사용할 수 있다.
      - name: 저장소 체크아웃
        uses: actions/checkout@v4
```

- 저장소 코드를 러너에 내려받음

---

```yml
      # 각 모듈이 Spring Boot 프로젝트라서 JDK 17을 먼저 준비한다.
      # cache: gradle 옵션은 의존성을 다시 받는 시간을 줄여서 빌드 속도를 안정적으로 만든다.
      - name: JDK 설정
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"
          cache: gradle
```

- JDK 17 세팅 + Gradle 캐시
- Spring Boot 모듈 빌드를 염두에 둔 구성

---

```yml
      # GHCR 경로는 소문자 저장소명이 가장 안전하므로 owner 값을 한 번 정리한다.
      # IMAGE_TAG는 현재 커밋 SHA 앞 7자리로 두어서
      # "어떤 코드에서 만들어진 이미지인지" 나중에 추적하기 쉽게 만든다.
      - name: 이미지 경로 값 준비
        shell: bash
        run: |
          echo "IMAGE_REGISTRY=ghcr.io/${GITHUB_REPOSITORY_OWNER,,}" >> "${GITHUB_ENV}"
          echo "IMAGE_TAG=${GITHUB_SHA::7}" >> "${GITHUB_ENV}"
```

- 이미지 관련 환경값 준비
- IMAGE_REGISTRY=${GITHUB_REPOSITORY_OWNER,,}
- IMAGE_TAG=${GITHUB_SHA::7}

---

```yml
      # GitHub Actions의 기본 토큰으로 GHCR 로그인까지 처리한다.
      # 별도 레지스트리 계정 비밀번호를 저장소 시크릿에 넣지 않아도 되는 장점이 있다.
      - name: GHCR 로그인
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
```

- GHCR로그인
- secrets.GITHUB_TOKEN 사용

---

```yml
      - name: Build and push image # Dockerfile 기반 이미지 빌드 및 푸시
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ steps.prepare-image.outputs.image }}
            ${{ steps.prepare-image.outputs.latest }}
          platforms: linux/amd64,linux/arm64
```

- Docker 이미지를 빌드하고 push
